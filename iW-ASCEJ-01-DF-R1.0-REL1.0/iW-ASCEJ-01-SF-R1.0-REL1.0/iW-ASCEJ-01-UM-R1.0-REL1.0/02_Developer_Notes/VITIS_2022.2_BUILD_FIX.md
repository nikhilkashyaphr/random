# Vitis 2022.2 (classic flow): `fatal error: xil_io.h: No such file or directory`

## This is not a source problem

`adcDisableCoeffOvrd.c` is one of the files never modified during the port, and
`xil_io.h` is a stock BSP header. Verified: **all 16 modules compile clean
against the 2022.2 BSP in the classic `DEVICE_ID` flow** (no `-DSDT`), using the
headers from your own `zu47dr_plat` archive.

The compiler is being pointed at an include directory that does not contain the
BSP headers **on this machine**.

## The single decisive check

```bat
dir "C:\Users\lakshya.nagesh\Desktop\Device_lock\Baremetal_update_47DR\A_test\zu47dr_plat\export\zu47dr_plat\sw\zu47dr_plat\standalone_domain\bspinclude\include\xil_io.h"
```

For reference, in the archive that path is populated with **134 headers**, plus
`libxil.a` and `libmetal.a` under `.../standalone_domain/bsplib/lib/`.

| Result | Cause | Fix |
|---|---|---|
| **Not found**, folder empty/absent | Platform never built on this machine — `export/` is generated by the platform build, not shipped | Right-click **`zu47dr_plat`** → **Build Project**. Then build the app. |
| **File is there** | App's include path doesn't match disk — stale absolute path from the other machine, or the `A_test` folder was renamed | Re-point the platform (below) |
| Folder exists, few headers | Partial/failed BSP generation | Platform → **Clean**, then **Build**. If it persists, delete `zu47dr_plat/export/` and rebuild. |

## Build order matters in 2022.2

The application's include path resolves into the **platform's** `export/` tree,
which only exists after the platform is built. A freshly cloned or copied
workspace has no `export/`, so the very first app build always fails this way.

**Platform first, application second.** Always.

## Re-pointing the platform (case B)

If the paths were carried over from another machine:

1. Right-click the application project → **Properties**
2. **C/C++ Build → Settings → ARM v8 gcc compiler → Directories**
3. Remove the stale `-I` entry, add the correct one for this machine
4. Also check **Project References**, and the **Platform** dropdown in the app's
   `.prj` editor — it must name the platform in *this* workspace

Cleanest alternative: create a new application component against the local
platform and copy `src/` in. That avoids every stale-path field at once.

## Windows path length

Not the cause here, but worth knowing — you have limited headroom:

| Path | Length | Limit |
|---|---|---|
| include dir | 155 | 260 |
| `xil_io.h` | 164 | 260 |
| `metal/processor/aarch64/gcc/atomic.h` | 192 | 260 |

That leaves ~68 characters, and Vitis build directories add more. `Desktop\
Device_lock\Baremetal_update_47DR\A_test\` is deep. If you hit strange
"file not found" errors on files that clearly exist, move the workspace to
something like `C:\work\zu47dr\`.

## Note on the two toolchains

You now have two environments:

| | Vitis 2022.2 (Windows) | Vitis 2025.2 (Linux) |
|---|---|---|
| Project | `zu47dr_app` | `app_component` |
| Flow | classic `XPAR_*_DEVICE_ID` | SDT `-DSDT`, BASEADDR |
| Platform | `zu47dr_plat` | `platform_ZU47` |

`platform_ids.h` handles both automatically — it selects the classic branch when
`SDT` is undefined. **One source tree, both toolchains**, verified against real
BSP headers for each. No `#ifdef` edits needed when moving between them.

One thing to keep aligned: `psu_init.c` was removed from `src/` for the 2025.2
build (the FSBL does PS init there). If your 2022.2 project expects it, add it
back **in that project only** — do not re-add it to the 2025.2 build.
